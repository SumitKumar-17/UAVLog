# TimescaleDB vs DuckDB on 70,731,891 telemetry rows

Median of 5 warm runs; DuckDB 1.5.6 with 4 threads, TimescaleDB 2.30.2 (client-server, default parallelism). DuckDB is embedded; concurrency is not measured.

## Storage

| representation | size | bytes per row |
|---|---|---|
| PostgreSQL rowstore + index (before compression) | 12459 MB | 176.15 |
| TimescaleDB columnstore | 385 MB | 5.44 |
| Parquet (zstd, sorted) | 392 MB | 5.54 |
| DuckDB native file | 700 MB | 9.90 |

## Query latency (p50)

| query | TimescaleDB columnstore | DuckDB over Parquet | DuckDB native table |
|---|---|---|---|
| Q1 one signal of one flight, 1 s buckets | 25.4 ms | 25.3 ms | 4.9 ms |
| Q2 one signal across all flights | 69.2 ms | 30.6 ms | 12.9 ms |
| Q3 every signal of one flight | 18.7 ms | 45.7 ms | 22.5 ms |
| Q4 one signal in a 90 day window | 3.8 ms | 28.4 ms | 4.5 ms |
| Q5 count and mean per signal, all data | 811.8 ms | 1057.8 ms | 478.3 ms |
| Q6 min/max/mean per flight and signal (the summary build) | 1007.5 ms | 2605.3 ms | 2004.0 ms |

## Load throughput

| path | rows per second |
|---|---|
| TimescaleDB COPY into a hypertable (uncompressed) | 286,792 |
| DuckDB row-by-row INSERT (200k rows, for contrast) | 603 |
| DuckDB bulk INSERT from Parquet | 6,153,564 |
| DuckDB write to Parquet | 4,034,708 |
