\begin{abstract}
\noindent UAV flight logs are treated as a database problem: a high-rate time series, a text layer of events, and an ontology that maps two autopilots' field names onto shared concepts, all in one PostgreSQL instance with TimescaleDB and pgvector. The report explains each concept in plain English first and the technical detail second. It documents the schema, the columnstore physical design, the semantic layer, hybrid and filtered vector search, a guarded natural-language-to-SQL interface, and the experiments that justify each choice. All figures are taken from the saved result files in \code{bench/results/} and the running database; every design decision is logged with its evidence in \code{docs/decisions.md}.
\end{abstract}

\section{The Big Picture}
A drone writes a \emph{flight log} on every flight: positions, attitudes, battery voltage, motor commands, and text messages such as warnings. One log is easy to look at. A \emph{collection} of logs is hard, because the data is three things at once.
\begin{itemize}
  \item \textbf{A dense time series.} The corpus has 300 real PX4 flights and 70.7 million telemetry samples.
  \item \textbf{Free text.} 3,401 events: warnings, failure flags, mode changes.
  \item \textbf{Vendor dialects.} PX4 and ArduPilot call the same physical quantity different things.
\end{itemize}
Today's tools show one flight at a time, yet the questions people ask span many flights and are asked in words (\emph{``which flights lost a motor?''}).

\begin{keyconcept}
\textbf{Thesis.} Treat the whole collection as a database problem. One PostgreSQL instance stores the time series compactly, maps vendor fields to shared meanings, searches events by meaning, and lets a language model answer questions in SQL under strict safety rules. Every design choice is justified by a measurement.
\end{keyconcept}

\shot[0.95]{diagram-architecture.png}{Architecture. Raw logs become a Parquet lake, the canonical telemetry hypertable and events; embeddings and the ontology sit beside them; the application reaches data only through search and guarded read-only views.}

\subsection{Research questions}
\begin{enumerate}
  \item \textbf{RQ1, storage.} How should high-rate telemetry be stored, and what does it cost? (Sections~\ref{sec:storage}, \ref{sec:engines})
  \item \textbf{RQ2, retrieval.} Which vector index and which filtering strategy retrieve events best, and does full-text fusion help? (Section~\ref{sec:search})
  \item \textbf{RQ3, natural-language access.} Can a model write safe, correct SQL, and what does a semantic layer add? (Section~\ref{sec:nlsql})
  \item \textbf{RQ4, detection.} Do the event detectors find faults of known size and duration? (Section~\ref{sec:events})
\end{enumerate}

\begin{insight}
Negative results are reported as carefully as positive ones. Hybrid text-plus-vector search did \emph{not} beat vector-only search, and the semantic views' gain in NL-to-SQL accuracy was \emph{not} statistically significant. Saying so is part of the method.
\end{insight}

\subsection{Gap in existing work}
Log viewers show one flight and know nothing about meaning. Time-series databases store the numbers but have no ontology or vendor mapping. NL-to-SQL demonstrations exist, but they are rarely guarded or measured. To our knowledge there is no published system that combines an ontology, hybrid retrieval and guarded natural-language SQL over PX4 logs.

\section{Core Concepts}
\subsection{Time series, hypertables and chunks}
\emph{Plain English:} a time series is a list of measurements stamped with a time. A \textbf{hypertable} (TimescaleDB) looks like one table but is silently cut into \emph{chunks}, one per time range, so recent data stays small and old data can be stored differently.
\begin{definition}
\textbf{Hypertable}: a logical table partitioned by time into chunks. Here, telemetry uses 7-day chunks (134 chunks for this corpus).
\end{definition}

\subsection{Columnstore and compression}
\emph{Plain English:} a normal table stores row by row. A columnstore stores each column together, so similar numbers sit side by side and compress extremely well, and a query that needs one signal reads only that signal.
\begin{definition}
\textbf{Columnstore with \code{segmentby}}: compressed chunk storage where rows are grouped by the \code{segmentby} columns and ordered by \code{orderby}. Here the grouping is (flight, signal), ordered by time, so one compressed row group holds one signal of one flight.
\end{definition}

\subsection{Continuous aggregates}
\emph{Plain English:} a rollup that the database keeps up to date. Here: min, max and mean per second per flight and signal, used so a zoomed-out chart does not read every sample.

\subsection{Embeddings and nearest-neighbour search}
\emph{Plain English:} an embedding turns text into a list of 1,536 numbers so that texts with similar meaning land near each other. Searching by meaning means finding the nearest points. Comparing against every point is exact but slow, so \emph{approximate} indexes trade a little accuracy for speed.
\begin{itemize}
  \item \textbf{HNSW}: a layered graph; hop from node to nearby node toward the query.
  \item \textbf{IVFFlat}: points are sorted into clusters; search only the closest few clusters.
  \item \textbf{DiskANN}: a compressed graph built to live mostly on disk (pgvectorscale).
\end{itemize}
\emph{Math:} recall@$k$ is the fraction of the true top-$k$ neighbours the index returns, $\text{recall}@k=|A\cap T|/k$, with $A$ the approximate and $T$ the exact result.

\subsection{The filtering pitfall}
\emph{Plain English:} pgvector finds the nearest neighbours first and applies the SQL filter afterwards. If the filter keeps one row in a thousand, the index may find 40 neighbours and none of them pass, so the query returns too few rows.

\subsection{Reciprocal rank fusion}
\emph{Plain English:} when two rankers disagree (vector similarity versus keyword match), fuse their \emph{ranks}, not their raw scores, because the scores are not comparable. \emph{Math:}
\[ \text{RRF}(d)=\sum_{i} \frac{w_i}{k+\text{rank}_i(d)} \]
with weights $w_i$ and a smoothing constant $k$ (here 60).

\subsection{Ontology as relational tables}
\emph{Plain English:} an ontology is a dictionary of concepts and how they relate. Here it is ordinary tables (concept, relation, vendor field, field mapping) walked with recursive queries.

\subsection{How retrieval and NL-to-SQL are measured}
\begin{description}
  \item[nDCG@10] ranking quality over the top 10 results, rewarding relevant results near the top.
  \item[Execution accuracy (EX)] share of generated queries whose \emph{result} equals the result of a reference query. \emph{Strict} requires the same columns and values; \emph{lenient} ignores extra columns.
  \item[Relative contrast (RC10)] how much farther the 10th neighbour is than the nearest; lower means harder data for any index.
  \item[Paired sign test] counts questions one condition gets right and another gets wrong, and asks whether the split is plausible under chance.
\end{description}

\section{Data and Environment}
\begin{itemize}
  \item \textbf{Corpus.} 300 flights chosen (seeded, stratified) from 478,918 public Flight Review PX4 logs (CC-BY); 8.75 GB of ULog files, parsed to a Parquet raw layer and the canonical telemetry table: 70,731,891 rows and 3,401 events.
  \item \textbf{Second autopilot.} An ArduPilot MAVLink log goes through the same ontology.
  \item \textbf{Environment.} 4 cores, 15 GB RAM, no GPU; PostgreSQL 17.11, TimescaleDB 2.30.2, pgvector 0.8.7, pgvectorscale 0.9.1, DuckDB 1.5.6, everything in Docker.
  \item \textbf{Method.} One connection, warm cache, 3 measured passes (vectors) or the median of 5--7 runs (storage); recall against exact search with 200 held-out queries, top 10; a development set and a separate held-out set for NL-to-SQL; bootstrap intervals and paired tests.
\end{itemize}

\begin{keyconcept}
\textbf{Hot fields in the database, the rest in Parquet.} Full-rate raw data (60--150 topics per log) stays in Parquet; the database holds the 34 ontology-mapped signals as \code{(flight\_id, ts, vendor\_field\_id, value)}. The trade-off, recorded in the decision log: a narrow table needs a join to name signals and cannot read two signals in one row without pivoting, but a wide per-topic table fits a changing schema (firmware drift) poorly.
\end{keyconcept}

\section{Contribution 6: Guarded Natural-Language SQL}\label{sec:nlsql}
\emph{Plain English:} a model that writes SQL could, if tricked, read server files or run a query that takes the server down. ``It only runs SELECT'' is not a safety boundary. The design uses four independent layers so defeating one is not enough.
\shot[0.9]{diagram-guard.png}{The guard pipeline.}
\begin{enumerate}
  \item \textbf{Guard} (\code{sqlglot}): exactly one SELECT, allow-listed tables and functions, no nested or recursive WITH; the SQL that runs is \emph{regenerated from the parse tree}, so what was checked is what runs.
  \item \textbf{Role}: a database role that can read only the documented views.
  \item \textbf{Read-only transaction} with an 8 s statement timeout.
  \item \textbf{Cost admission}: \code{EXPLAIN} first; refuse when the planner's estimate exceeds 100,000.
\end{enumerate}

\section{Design Decisions}
The decision log (\code{docs/decisions.md}) records what, why and the alternatives for each choice. The ones that shaped the database:
\begin{description}
  \item[D1] One Postgres with TimescaleDB and pgvector as the core store (polyglot alternatives rejected for operational weight and because they hide the planner trade-offs studied here).
  \item[D2] Narrow telemetry table with only ontology-mapped signals; everything else stays in Parquet.
  \item[D3] Columnstore with \code{segmentby (flight\_id, vendor\_field\_id)}, \code{orderby ts}.
  \item[D4] Compression as an explicit, repeatable stage that also handles partial chunks.
  \item[D6] Data-quality guards at ingest (implausible device clocks).
  \item[D7] Events from log transitions and threshold rules.
  \item[D11--D13] Hybrid retrieval with RRF; measured result that vector wins and no absolute relevance cutoff exists.
  \item[D15] Robust flight duration after one corrupt timestamp.
  \item[D16] NL-to-SQL guarded, read-only and measured with and without the semantic layer.
\end{description}

\section{Glossary}
\begin{description}
  \item[Hypertable] Time-partitioned table in TimescaleDB.
  \item[Chunk] One time-range partition of a hypertable.
  \item[Columnstore] Compressed column-wise storage of older chunks.
  \item[Continuous aggregate] Incrementally maintained rollup (here 1-second min, max, mean).
  \item[Embedding] A list of numbers representing meaning; here 1,536 dimensions for events and 32 for flight signatures.
  \item[HNSW / IVFFlat / DiskANN] Approximate nearest-neighbour index families.
  \item[Recall@k] Fraction of the true top-$k$ returned.
  \item[nDCG@10] Ranking quality over the top 10.
  \item[RRF] Reciprocal rank fusion of several rankings.
  \item[Ontology] Concepts and relations; here stored in relational tables.
  \item[Gaps and islands] SQL pattern that finds runs of consecutive rows.
  \item[SKIP LOCKED] Row-locking mode that skips rows another transaction holds; used by the job tables.
  \item[Execution accuracy] Share of generated queries whose result equals the gold result.
  \item[RC10] Relative contrast of the 10th neighbour; lower means harder data.
  \item[Parquet] Open columnar file format used for the raw layer.
\end{description}

\section{Frequently Asked Questions}
\paragraph{Why one database instead of several specialised ones?}
Transactions, roles, joins to the ontology and vectors then live together, and the planner trade-offs become the object of study. DuckDB won some scans in the comparison but gives up concurrent writers and roles.

\paragraph{Why a narrow telemetry table?}
New signals and new autopilots then need no schema change, and the ontology can map any vendor field. The cost is more rows and a join to name signals; the columnstore turns the extra rows into 5.4 bytes each.

\paragraph{Is 300 flights enough?}
It is a stated limit. Storage results are measured on 70.7 million rows; vector benchmarks use 50,000 and 100,000 perturbed vectors made harder than the real data. A larger run on 10,000 or more logs is the next step and every volume is configurable.

\paragraph{Why did hybrid search lose?}
On 65 queries vector similarity already handles paraphrases, and plain fusion lets weak keyword hits displace good vector hits. With a small keyword weight it ties; no evidence was found that it helps.

\paragraph{Why did the planner choose the wrong plan?}
Its cost model estimates time, not result completeness. HNSW post-filtering looks cheap but returns 4 of 10 rows. The router avoids depending on that estimate for correctness.

\paragraph{Is the NL-to-SQL ``safe''?}
It is defended in four independent layers and tested with 46 hostile queries. The remaining risk is correctness (confident wrong answers), which is why the SQL and its cost are shown with every answer.

\paragraph{The views added 0.19 accuracy but it is ``not significant''. Is it useful?}
The direction is positive (six questions gained, one lost) but 27 questions cannot separate it from chance ($p=0.125$). The clear effect is documentation.

\paragraph{What is the weakest result?}
The battery-low detector: it is silent below its minimum duration and raises false alarms on 23\% of unmodified flights.

\section{Conclusions}
\begin{itemize}
  \item A single PostgreSQL instance holds the time series, the ontology, the vectors and a guarded natural-language interface.
  \item Physical design cut telemetry from 12.5 GB to 385 MB (32$\times$); measured, not assumed.
  \item For retrieval, filtering strategy mattered more than index choice, and a self-routing query beat any fixed plan.
  \item Documentation, more than views, drives NL-to-SQL accuracy; four independent layers make it safe.
  \item Detectors find injected faults reliably from 5 s, with a known weakness in the battery rule.
\end{itemize}
\textbf{Limits.} 300 flights, one machine, one model, author-written questions, perturbed vectors for index benchmarks, heuristic event thresholds. \textbf{Next.} The 10,000-log run, ArduPilot at scale, a concurrency benchmark.
